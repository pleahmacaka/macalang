# evals

pass@1 over HumanEval, ported to Maca, measured against what the model was
told. Without a number, "the specification helps" is an opinion.

## Running it

```sh
curl -sSLO https://raw.githubusercontent.com/openai/human-eval/master/data/HumanEval.jsonl.gz
gunzip HumanEval.jsonl.gz
maca run apps/evals/port.maca HumanEval.jsonl     # writes problems/
MACA_EVAL_MODEL=./your-model maca run apps/evals/run.maca
```

`apps/` is not an import search root, so these are reached by path rather than
as `-m evals`. Both are run from the top of the repository.

`MACA_EVAL_MODEL` is a command taking one argument, the path to a prompt file,
and writing Maca to stdout. Anything that satisfies that works, so the harness
does not know or care which model it is measuring. Without one, every problem
fails with `no MACA_EVAL_MODEL` rather than a fabricated number.

## The three conditions

| condition | the model is given |
|---|---|
| no spec | the problem, and that Maca is the language |
| spec | the problem, after `maca spec --llm` |
| spec + one check retry | the same, and on failure the `maca check --json` output once |

The third is the one the whole plan is about: whether a structured diagnostic
lets a model recover from its own mistake.

## The port is mechanical

`port.maca` translates a problem when every parameter, the result and every
assertion have a Maca form: `int`, `float`, `str`, `bool` and lists of those.
25 of 164 do. The other 139 are in `problems/SKIPPED.md` with the reason, which
makes that file a work queue: a form added to the porter moves a problem out of
it and into the set.

Nothing here is hand-written. A hand-ported problem would be a problem whose
translation nobody can check, and the point of the number is that it is
comparable.

## Grading

The answer is written where the stub was, the test the porter generated is left
alone, and the file is checked and run. Pass and fail come from the exit
status. They used to come from matching the runner's output for
`tests passed`, which scored a correct solution zero because a one-test file
says `1 test passed`.

## The baseline

`BASELINE.md` is regenerated by a run and committed, so a change to the
specification or to the diagnostics shows up as a moved number rather than an
impression. The committed one is a real run against `models/claude.sh`.

**One run is one sample.** The set is 25 problems and the model is not
deterministic, so one solved problem is four points and a difference of one or
two is noise. Three runs of the same toolchain gave:

| condition | run 1 | run 2 | run 3 |
|---|---|---|---|
| no spec | 12% | 12% | 4% |
| spec | 36% | 40% | 32% |
| spec + one check retry | 36% | 36% | 40% |

Read that as: **the specification moves pass@1 a long way**, from under a tenth
to about a third. **One `maca check --json` retry does not**, at least not at
this set size, where its three results straddle the plain `spec` column. A
claim about the retry needs more problems or more runs per problem; the number
here is not evidence for it, and the point of writing the numbers down is to be
able to say so.
