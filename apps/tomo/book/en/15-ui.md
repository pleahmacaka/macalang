# Interfaces and Documents

Maca has a syntax for HTML elements and a stylesheet generator that reads the
classes you write. Both are part of the language, not a library. The same markup
becomes a live DOM in the browser and a string of HTML in a native binary.

The page you are reading was produced by it.

## An element is a call

Any HTML tag name can be called:

```maca
article(class="prose",
    h1("Hello")
    span("Some text"))
```

Named arguments are attributes; positional arguments are children. Children are
separated by commas or by nothing at all.

An element is an ordinary expression, so it composes with everything else: build
one in a function, put one in a list, return one from a `match`.

```maca
item(name: str) -> str => li(name)

list_of(names: str[]) -> str =>
    ul(names.map(item).join(""))
```

## Two targets, one syntax

```
maca build app.maca --target js -o out
```

builds a reactive page: elements become `createElement` calls, `onclick=`
attaches a handler, and `value=` on a state name binds it two ways. The names
are the platform's own, so `oninput=`, `ondragstart=` and `ondrop=` are spelled
as in HTML.

```maca
count = 0

bump() { count = count + 1 }

main() -> Element =>
    div(
        button(onclick=bump, "+")
        span("{count}")
    )
```

There is no repaint call in that program. **Assigning a declared name is the
update**: `count = count + 1` marks `count` changed, and the nodes that read
`count` run again. A handler that assigns three names still repaints once, when
it returns, and a loop that assigns the same name a hundred times repaints once,
after the loop.

`update()` still exists, for when something outside Maca moved and the view has
no way to know. That is what `maca.refresh()` is in the bridge an `import js`
block talks through.

```
maca build gen.maca -o gen
```

builds a native binary, and there the same elements render to **text**:

```maca
main() -> int {
    info(article(class="prose", h1("Hi") span("Body")))
    0
}
```

```
<article class="prose"><h1>Hi</h1><span>Body</span></article>
```

An event handler has nowhere to attach in a string, so the older `on:click=`
directive on the native target is a compile error that tells you to build for
`js`. A vanilla `onclick="…"` is an ordinary HTML attribute there.

## A definition wins over a tag

`label`, `code`, `main`, `section`, `p`, `a`, `form` and `option` are HTML tags
*and* names people give their own functions. When a name is defined, the
definition wins:

```maca
label(pos: bool) -> str => pos ? "right" : "left"

main() -> int {
    info(label(true))     // "right": your function, not <label>
    info(span("tag"))     // "<span>tag</span>": nothing shadows `span`
    0
}
```

This is the ordinary scoping rule, applied before the tag is considered.

## A view can contribute a list of elements

A child may be a **list** of elements, and then each element of the list is a
child in its place:

```maca
Link = { title: str, icon: str }

pencil(on: bool) -> Element[] {
    if !on {
        return []
    }

    [button(class="pencil", "edit")]
}

row(link: Link, on: bool) -> Element =>
    li(class="row",
       [i(class="icon", link.icon), span(class="title", link.title)]
           ++ pencil(on))
```

`Element` is the type of a rendered element, and `Element[]` a list of them.
`[]` contributes **nothing at all**: no node on the JS target, no markup on the
native one. A view that has nothing to show returns the empty list, rather than
an element carrying `class="hidden"` that the browser still has to build and lay
out.

`++` joins two element lists, `.map` produces one, and a list literal is one
written out. All four arrive at a parent the same way:

```maca
ul(links.map(l => row(l, editing)))
```

A function has to say so in its signature: `-> Element` or `-> Element[]` tells
the compiler this call hands back nodes rather than text. A function returning
`str` is still a child rendered as text.

## Styles are generated, not linked

Classes are written in `class=` using Tailwind's utility names, and the compiler
generates the stylesheet for the utilities your program actually mentions.
`styles()` returns it as a string:

```maca
page() -> str =>
    div(class="max-w-2xl mx-auto font-bold", "text")
```

```css
.font-bold { font-weight:700; }
.max-w-2xl { max-width:42rem; }
.mx-auto { margin-left:auto;margin-right:auto; }
```

One rule per utility written. A utility the program never mentions produces no
rule, and there is no network fetch.

## Write one

A page, complete, with no other files:

```maca
main() -> int {
    write_file("index.html",
        "<!doctype html>\n"
        ++ html(lang="en",
            head(
                meta(charset="utf-8")
                meta(name="viewport", content="width=device-width,initial-scale=1")
                title("Notes")
                style(styles()))
            body(class="font-serif bg-white dark:bg-zinc-900",
                element("main",
                    h1(class="text-[2rem] font-bold", "Notes")
                    span(class="my-4", "Written in Maca.")))))
    0
}
```

`maca run` it and you have a styled, self-contained, dark-mode-aware page.

## Where the full answer is

[The UI Syntax](a11-ui.md) in the reference has the sharp edges: hyphenated
attributes and the attached-versus-spaced rule that makes them work, boolean
attributes that control an attribute's *presence*, `element(tag, …)` for a tag
chosen at run time, the full variant tables (`hover:`, `dark:`, `max-md:` and
how they combine), arbitrary values in brackets, and the one place classes are
**not** collected: inside a raw `"""…"""` string.
