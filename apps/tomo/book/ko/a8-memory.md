# 메모리와 소유권

컴파일러가 어떤 값이 다 쓰였다고 판단할 때 따르는 규칙입니다. 왜 이렇게 하는지는
[GC 없는 메모리 관리](04-memory.md)입니다.

## 컴파일러가 넣어 주는 것

모든 힙 블록은 소유자가 몇인지를 세고 다닙니다. `maca_alloc`은 소유자가 하나인
블록을 돌려주고, 소유자를 더하고 빼는 호출은 컴파일러가 넣습니다. 마지막
소유자가 손을 놓으면 블록은 free-list로 갑니다.

**지역 변수는 자기가 만들었고 자기 블록보다 오래 살 수 없을 때 그 버퍼를
소유합니다.** 다른 이름에서 받아온 값은 별칭이고 아무것도 소유하지 않습니다.
어떤 식으로든 밖으로 나간 값은 받은 쪽의 것이고, 나머지는 블록이 끝날 때 놓아
줍니다.

값을 읽는 것은 가져가는 것이 아니므로 메서드 호출은 소유권을 그대로 둡니다.

효과는 프로그램 안에서 그대로 보입니다.

```maca
build(n: int) -> int[] {
    xs = []
    for i in 0..n {
        xs = xs.push(i)
    }
    xs
}

main() -> int {
    for round in 0..500 {
        ys = build(200)
    }
    info("할당의 {reuse_count() * 100 / alloc_count()}% 를 재사용")
    0
}
```

90%가 넘습니다. `alloc_count()`와 `reuse_count()`는 릴리스 바이너리에서도 같은
값을 주는 런타임 카운터라, 프로그램이 자기 할당 동작을 테스트에서 단언할 수
있습니다.

## 탈출 분석은 일부러 한쪽으로 기울어 있습니다

밖으로 나가는 것을 놓치면 남이 아직 들고 있는 버퍼를 해제하게 되지만, 나가지
*않는* 것을 놓치면 필요보다 조금 더 오래 들고 있을 뿐입니다. 그래서 판단이
서지 않으면 컴파일러는 값을 그대로 둡니다.

최대 메모리 측정은 공정한 숫자이지만 *즉시성* 측정은 늘 그렇지는 않습니다.
죽었다고 증명하지 못한 값은 자기 블록 끝까지 삽니다.

## 재사용

어떤 값의 소유자 수가 1이고 곧 그 값이 재구성될 참이면, 해제 후 재할당하는
대신 메모리를 그 자리에서 재사용합니다.

| 이렇게 쓰면 | 입력을 단독으로 소유할 때 컴파일되는 것 |
|---|---|
| `p with { f = v }` | `p`의 메모리에 대한 필드 저장 |
| `xs.map(f)` | `xs`의 버퍼를 걸으며 각 칸에 쓰기 |
| `xs.push(x)` | `xs`의 버퍼 확장 |
| `xs.sort()` | `xs`의 버퍼 정렬 |

단독으로 소유하고 있지 *않으면* 같은 식이 할당을 하고 원본은 그대로입니다.
관찰되는 의미는 양쪽이 같습니다.

## 순환

참조 카운팅은 순환을 수거하지 못하고, Maca는 순환 수집기를 돌리지 않습니다.
트리, 리스트, AST는 모두 비순환이라 괜찮습니다. 각 노드가 부모를 다시 가리키는
이중 연결 리스트는 프로세스가 끝날 때까지 스스로를 살려 둡니다. 여기에 대한
진단은 없습니다.

## 재귀 타입이 치르는 비용

**재귀 합타입 페이로드**는 박싱됩니다. `Tree = Leaf | Node(int, Tree, Tree)`는
노드마다 할당하고, 페이로드를 바인딩하는 `match`가 그것을 역참조합니다.

**재귀 레코드 필드**는 C에서 정의 순환입니다. 백엔드는 레코드 본문 *앞에* 배열
구조체 선언을(`MACA_ARRAY_STRUCT`), 본문 *뒤에* 배열 연산을(`MACA_ARRAY_OPS`)
내보내어 순환을 끊습니다.

```maca
Expr = {
    kind: int
    text: str
    children: Expr[]
}
```

셀프호스팅 AST가 필요로 했기 때문에 존재합니다.
[셀프호스팅 컴파일러](a15-self-hosting.md)를 보세요.

## 없는 것

`mut`도, `&`도, 라이프타임도, `clone()`도, `Rc`도, `unsafe`도 없습니다.
컴파일러가 증명할 수 있는 것을 증명하고 못 하는 것은 세며, 표면 문법에는
어느 쪽인지를 말할 자리가 없습니다.
