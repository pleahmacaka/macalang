# 메모리와 소유권

컴파일러가 어떤 값이 다 쓰였다고 판단할 때 따르는 규칙입니다. 왜 이렇게 하는지는
[GC 없는 메모리 관리](04-memory.md)이고, 이 장은 무엇을 하는지입니다.

여기 있는 것 중 직접 쓰는 것은 하나도 없습니다. 메모리가 왜 그렇게 움직이는지를
설명하기 때문에, 그리고 규칙 둘은 프로그램 안에서 관찰할 수 있는 결과를 갖기
때문에 여기 있습니다.

## 컴파일러가 넣어 주는 것

모든 힙 블록은 소유자가 몇인지를 세고 다닙니다. `maca_alloc`은 소유자가 하나인
블록을 돌려주고, 소유자를 더하고 빼는 호출은 컴파일러가 넣습니다. 마지막
소유자가 손을 놓으면 블록은 free-list로 가고, 같은 크기의 다음 요청이 그것을
집어 갑니다.

이 호출들을 직접 쓸 일은 없습니다. 그래도 컴파일러가 따르는 규칙은 알아 둘
값이 있는데, 메모리가 왜 그렇게 움직이는지를 설명하기 때문입니다.

**지역 변수는 자기가 만들었고 자기 블록보다 오래 살 수 없을 때 그 버퍼를
소유합니다.** 다른 이름에서 받아온 값은 별칭이고 아무것도 소유하지 않습니다.
블록의 결과로, 바깥 바인딩에, 구조체 안에, 인자로 — 어떤 식으로든 밖으로 나간
값은 받은 쪽의 것입니다. 나머지는 블록이 끝날 때 놓아 줍니다.

값을 읽는 것은 가져가는 것이 아니므로, 메서드 호출은 소유권을 그대로 둡니다.
`xs.length()`도 `xs.sort()`도 `xs`를 만든 블록에 그대로 남겨 둡니다. 이게
중요한 이유는, 한 번도 들여다보지 않을 값이라면 애초에 만들 이유가 없기
때문입니다.

효과는 프로그램 안에서 그대로 보입니다.

```maca
build(n: int) -> int[] {
    xs = []
    for i in 1..n {
        xs = xs.push(i)
    }
    xs
}

main() -> int {
    for round in 1..500 {
        ys = build(200)
    }
    info("할당의 {reuse_count() * 100 / alloc_count()}% 를 재사용")
    0
}
```

90%가 넘습니다. 루프는 버퍼 하나에 정착해서 할당기와 주고받을 뿐, 500개를
요구하지 않습니다.

`alloc_count()`와 `reuse_count()`는 디버그 빌드의 계측이 아니라 런타임
카운터입니다. 릴리스 바이너리에서도 같은 두 숫자이므로, 프로그램이 자기
할당 동작을 테스트에서 단언할 수 있습니다.

## 탈출 분석은 일부러 한쪽으로 기울어 있습니다

밖으로 나가는 것을 놓치면 남이 아직 들고 있는 버퍼를 해제하게 되지만, 나가지
*않는* 것을 놓치면 필요보다 조금 더 오래 들고 있을 뿐입니다. 그래서 판단이
서지 않으면 컴파일러는 값을 그대로 둡니다.

테스트 스위트 전체가 valgrind에 깨끗한 이유가 그것입니다. 살아 있는 것은 절대
놓아 주지 않고, 프로그램이 끝날 때까지 들고 있던 것은 그때 비웁니다. 최대
메모리 측정은 공정한 숫자이지만 *즉시성* 측정은 늘 그렇지는 않다는 뜻이기도
합니다. 죽었다고 증명하지 못한 값은 자기 블록 끝까지 삽니다.

## 재사용

어떤 값의 소유자 수가 1이고 곧 그 값이 재구성될 참이면, 해제 후 재할당하는
대신 메모리를 그 자리에서 재사용합니다.

| 이렇게 쓰면 | 입력을 단독으로 소유할 때 컴파일되는 것 |
|---|---|
| `p with { f = v }` | `p`의 메모리에 대한 필드 저장 |
| `xs.map(f)` | `xs`의 버퍼를 걸으며 각 칸에 쓰기 |
| `xs.push(x)` | `xs`의 버퍼 확장 |
| `xs.sort()` | `xs`의 버퍼 정렬 |

단독으로 소유하고 있지 *않으면* — 다른 무언가가 아직 들고 있으면 — 같은 식이
할당을 하고 원본은 그대로입니다. 관찰되는 의미는 양쪽이 같고, 그것이 요점입니다.
함수형 읽기는 언제나 옳고, 아무도 보고 있지 않을 때 명령형의 비용이 나옵니다.

## 순환

참조 카운팅은 순환을 수거하지 못하고, Maca는 순환 수집기를 돌리지 않습니다.
트리, 리스트, AST는 모두 비순환이고 모두 괜찮습니다. 각 노드가 부모를 다시
가리키는 이중 연결 리스트는 프로세스가 끝날 때까지 스스로를 살려 둡니다.

여기에 대한 진단은 없습니다. 이 언어가 배제하지 못하는 유일한 메모리 버그이고,
그래도 견딜 만한 이유는 그런 모양이 일부러 만들어야 나오는 모양이기
때문입니다. 셀프호스팅 컴파일러는 전부 트리로만 만들어진 큰 프로그램입니다.

## 재귀 타입이 치르는 비용

백엔드의 도움이 필요한 모양이 둘 있고, 둘 다 실제 프로그램이 원하는 모양입니다.

**재귀 합타입 페이로드**는 박싱됩니다. 힙 포인터가 되어 태그 유니언의 크기가
유한하게 유지됩니다. `Tree = Leaf | Node(int, Tree, Tree)`는 노드마다 할당하고,
페이로드를 바인딩하는 `match`가 그것을 역참조합니다.

**재귀 레코드 필드**는 C에서 정의 순환입니다. 배열 타입은 구조체의 크기를,
구조체는 배열을 필요로 합니다. 백엔드는 레코드 본문 *앞에* 배열 구조체 선언을
(`MACA_ARRAY_STRUCT`), 본문 *뒤에* 배열 연산을 (`MACA_ARRAY_OPS`) 내보내어
순환을 끊습니다. 소스에 전방 참조를 쓸 필요가 없습니다.

```maca
Expr = {
    kind: int
    text: str
    children: Expr[]
}
```

우연이 아니라 지원되는 모양이고, 셀프호스팅 AST가 필요로 했기 때문에
존재합니다. [셀프호스팅 컴파일러](a15-self-hosting.md)를 보세요.

## 없는 것

`mut`도, `&`도, 라이프타임도, `clone()`도, `Rc`도, `unsafe`도 없습니다.
그것들은 프로그래머가 소유권을 증명하는 체계의 어휘입니다. 여기서는 컴파일러가
증명할 수 있는 것을 증명하고 못 하는 것은 세며, 표면 문법에는 어느 쪽인지를
말할 자리가 아예 없습니다.
