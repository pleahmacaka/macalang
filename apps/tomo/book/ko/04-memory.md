# GC 없는 메모리 관리

메모리를 언제 되돌려줄지에 대한 답은 대략 셋으로 갈립니다.

- **수동**: 당신이 정합니다. C, Zig. 빠르고, 지금까지 출시된 보안 버그의 상당
  부분이 여기서 나왔습니다.
- **추적 GC**: 수집기가 알아냅니다. Go, Java, JavaScript. 안전하지만 런타임과
  일시 정지, 메모리 사용량의 하한을 대가로 냅니다.
- **정적 소유권**: 컴파일러가 증명합니다. Rust. 안전하고 빠르지만 라이프타임,
  빌림, 그리고 학습 절벽을 치릅니다.

Maca는 네 번째 길을 택합니다.

## 목표

C급 바이너리를 런타임 없이, 일시 정지 없이. 그러면서도 화요일 하루에 가르칠 수
있는 언어. 이 조건이 추적 GC와 빌림 검사를 모두 배제하고, **참조 카운팅**이
남습니다.

참조 카운팅의 고전적인 반론은 느리다는 것과 순환을 누수한다는 것입니다. 첫
번째는 대체로 순진한 구현의 산물입니다. 실제 프로그램에서 카운터 갱신 대부분은
불필요함을 증명할 수 있고, 컴파일 타임에 제거할 수 있습니다.

## Perceus 요약

Perceus(*precise reference counting with reuse and specialization*)는 Koka
언어에서 왔습니다.

1. 컴파일러가 Rust처럼 소유권을 정적으로 추적하되, 거기에 들어맞지 않는
   프로그램을 **거부하지는** 않습니다. 소유권이 분명한 곳에서는 카운터 조작을
   내보내지 않고, 분명하지 않은 곳에서만 런타임 카운트로 물러섭니다.
2. 어떤 값의 카운트가 1이 되고 곧 재구성될 참이면, 해제 후 재할당하는 대신
   메모리를 **그 자리에서 재사용**합니다.

관용적인 함수형 코드가 가변 버퍼로 직접 짰을 법한 코드와 거의 같은 것으로
컴파일됩니다. `p with { y = 5 }`라고 쓰면 제자리 필드 저장이 나옵니다.

`mut`도, `&`도, 라이프타임도, `clone()`도 없는 이유가 이것입니다. 여기서는
컴파일러가 소유권을 증명하고, 증명하지 못하는 곳에서만 세기만 합니다.

## 코드를 쓸 때 무엇이 달라지나

**공유된 것을 변경하기보다 새 값을 만드세요.** `base with { f = v }`는 아무도
`base`를 붙들고 있지 않을 때 복사가 아니라 저장입니다. 뻔한 함수형 스타일로 쓴
코드가 곧 최적화기가 겨냥하는 코드입니다.

```maca
Point = {
    x: int
    y: int
}

move_up(p: Point) -> Point =>
    p with { y = p.y + 1 }
```

**참조 순환을 만들어 놓고 사라지길 기대하지 마세요.** 참조 카운팅은 순환을
수거하지 못하고, Maca는 순환 수집기를 돌리지 않습니다. 트리, 리스트, AST는 전부
비순환이라 괜찮습니다. 각 노드가 부모를 다시 가리키는 이중 연결 리스트는
스스로를 살려 둡니다.

## 눈으로 확인할 수 있습니다

할당기는 카운터를 둘 유지하고, 프로그램이 그것을 읽을 수 있습니다.

```maca
build(n: int) -> int[] {
    xs = []
    for i in 0..n {
        xs = xs.push(i)
    }
    xs
}

main() -> int {
    for round in 0..500 {
        ys = build(200)
    }
    info("할당의 {reuse_count() * 100 / alloc_count()}% 를 재사용")
    0
}
```

90%가 넘습니다. 루프는 버퍼 하나에 정착해서 500개를 요구하지 않습니다. 200개짜리
리스트를 500번 다시 만드는데 할당은 거의 없습니다.

컴파일러가 따르는 정확한 규칙(어떤 지역 변수가 무엇을 소유하는지, 값이 언제
밖으로 나가는지, 재귀 타입이 무엇을 치르는지)은 레퍼런스의
[메모리와 소유권](a8-memory.md)에 있습니다.
