# GC 없는 메모리 관리

모든 언어는 메모리를 언제 되돌려줄지에 답해야 합니다. 답은 대략 셋으로
갈립니다.

- **수동** — 당신이 정합니다. C, Zig. 빠르고, 지금까지 출시된 보안 버그의 상당
  부분이 여기서 나왔습니다.
- **추적 GC** — 수집기가 알아냅니다. Go, Java, JavaScript. 안전하지만 런타임과
  일시 정지, 그리고 메모리 사용량의 하한을 대가로 냅니다.
- **정적 소유권** — 컴파일러가 증명합니다. Rust. 안전하고 빠르지만, 타입
  시스템으로 값을 치릅니다. 라이프타임, 빌림, 그리고 진짜배기 학습 절벽.

Maca는 네 번째 길을 택합니다. 그 **이유**를 이해할 가치가 있는데, 언어의 나머지
많은 부분을 설명해 주기 때문입니다.

## 목표

Maca는 C급 바이너리를 목표로 합니다. 런타임 없이, 일시 정지 없이. 그러면서도
화요일 하루에 가르칠 수 있는 언어여야 합니다. 이 조건이 추적 GC(런타임 때문에)와
빌림 검사(절벽 때문에)를 모두 배제합니다. 남는 것은 **참조 카운팅**인데, 이제는
대체로 부당한 악평을 받고 있습니다.

참조 카운팅에 대한 고전적인 반론은 느리다는 것(대입할 때마다 카운터를 건드림)과
순환을 누수한다는 것입니다. 첫 번째는 대체로 순진한 구현의 산물입니다. 실제
프로그램에서 카운터 갱신 대부분은 불필요함을 증명할 수 있고, 컴파일 타임에
제거할 수 있습니다. 이 관찰이 Maca가 기반으로 삼은 **Perceus**의 출발점입니다.

## Perceus 요약

Perceus — *precise reference counting with reuse and specialization* — 는 Koka
언어에서 왔습니다. 핵심 아이디어는 이렇습니다.

1. 컴파일러가 Rust처럼 소유권을 정적으로 추적하되, 거기에 들어맞지 않는
   프로그램을 **거부하지는** 않습니다. 소유권이 분명한 곳에서는 카운터 조작을
   아예 내보내지 않고, 분명하지 않은 곳에서만 런타임 카운트로 물러섭니다.
2. 어떤 값의 카운트가 1이 되고 곧 그 값이 재구성될 참이면, 해제 후 재할당하는
   대신 메모리를 **그 자리에서 재사용**합니다. 레코드에 대한 `with` 갱신이나
   리스트에 대한 map이 이미 가지고 있던 버퍼를 변경하는 코드로 컴파일될 수
   있습니다.

결과적으로, 관용적인 함수형 코드 — 낡은 값에서 새 값을 만드는 코드 — 가 가변
버퍼로 직접 짰을 법한 코드와 거의 같은 것으로 컴파일됩니다. `p with { y = 5 }`
라고 쓰면 제자리 필드 저장이 나옵니다.

Maca에 `mut`도, `&`도, 라이프타임도, `clone()`도 없는 이유가 이것입니다. 그것들은
*당신이* 소유권을 증명하는 체계의 어휘입니다. 여기서는 컴파일러가 증명하고,
증명하지 못하는 곳에서는 조용히 세기만 합니다.

## 코드를 쓸 때 무엇이 달라지나

대부분은 아무것도 달라지지 않습니다. 그것이 요점입니다. 다만 두 가지 습관이
따라옵니다.

**공유된 것을 변경하기보다 새 값을 만드세요.** `base with { f = v }`는 일반적으로
복사가 아닙니다. 아무도 `base`를 붙들고 있지 않을 때 이것은 저장입니다. 뻔한
함수형 스타일로 쓴 코드가 곧 최적화기가 겨냥하는 코드입니다.

```maca
Point = {
    x: int
    y: int
}

move_up(p: Point) -> Point =>
    p with { y = p.y + 1 }
```

**참조 순환을 만들어 놓고 사라지길 기대하지 마세요.** 참조 카운팅은 순환을
수거하지 못하고, Maca는 순환 수집기를 돌리지 않습니다. 트리, 리스트, AST는 모두
괜찮습니다. 전부 비순환이니까요. 각 노드가 부모를 다시 가리키는 이중 연결
리스트는 스스로를 살려 둡니다. 실제로는 거의 제약이 되지 않습니다. `selfhost/`의
컴파일러는 전부 트리로만 만들어진 큰 프로그램입니다.

## 컴파일러가 넣어 주는 것

모든 힙 블록은 소유자가 몇인지를 세고 다닙니다. `maca_alloc` 은 소유자가 하나인
블록을 돌려주고, 소유자를 더하고 빼는 호출은 컴파일러가 넣습니다. 마지막
소유자가 손을 놓으면 블록은 free-list로 가고, 같은 크기의 다음 요청이 그것을
집어 갑니다.

이 호출들을 직접 쓸 일은 없습니다. 그래도 컴파일러가 따르는 규칙은 알아 둘
값이 있는데, 메모리가 왜 그렇게 움직이는지를 설명하기 때문입니다.

**지역 변수는 자기가 만들었고 자기 블록보다 오래 살 수 없을 때 그 버퍼를
소유합니다.** 다른 이름에서 받아온 값은 별칭이고 아무것도 소유하지 않습니다.
블록의 결과로, 바깥 바인딩에, 구조체 안에, 인자로 — 어떤 식으로든 밖으로 나간
값은 받은 쪽의 것입니다. 나머지는 블록이 끝날 때 놓아 줍니다.

값을 읽는 것은 가져가는 것이 아니므로, 메서드 호출은 소유권을 그대로 둡니다.
`xs.length()` 도 `xs.sort()` 도 `xs` 를 만든 블록에 그대로 남겨 둡니다. 이게
중요한 이유는, 한 번도 들여다보지 않을 값이라면 애초에 만들 이유가 없기
때문입니다.

효과는 프로그램 안에서 그대로 보입니다.

```maca
build(n: int) -> int[] {
    xs = []
    for i in 1..n {
        xs = xs.push(i)
    }
    xs
}

main() -> int {
    for round in 1..500 {
        ys = build(200)
    }
    info("할당의 {reuse_count() * 100 / alloc_count()}% 를 재사용")
    0
}
```

90%가 넘습니다. 루프는 버퍼 하나에 정착해서 할당기와 주고받을 뿐, 500개를
요구하지 않습니다.

이 분석은 일부러 한쪽으로 기울어 있습니다. 밖으로 나가는 것을 놓치면 남이 아직
들고 있는 버퍼를 해제하게 되지만, 나가지 *않는* 것을 놓치면 필요보다 조금 더
오래 들고 있을 뿐입니다. 그래서 판단이 서지 않으면 컴파일러는 값을 그대로
둡니다. 테스트 스위트 전체가 valgrind에 깨끗한 이유가 그것입니다. 살아 있는
것은 절대 놓아 주지 않고, 프로그램이 끝날 때까지 들고 있던 것은 그때 비웁니다.

## 한눈에 비교

| | 런타임 | 즉시 해제 | 순환 처리 | 학습 비용 |
|---|---|---|---|---|
| 수동 (C) | 없음 | 당신이 하면 | 당신이 하면 | 높음, 버그로 |
| 추적 GC (Go) | 있음 | 아니오 | 예 | 없음 |
| 소유권 (Rust) | 없음 | 예 | 노력하면 | 높음, 타입으로 |
| Perceus (Maca) | 없음 | 예 | 아니오 | 없음 |
