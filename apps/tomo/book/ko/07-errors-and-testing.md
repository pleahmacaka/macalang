# 오류와 테스트

## 실패는 예외가 아니라 값이다

실패할 수 있는 함수는 실패함으로써 그것을 말합니다 — `fail msg`는 가장 가까운
핸들러까지 되감습니다:

```
divide(a: int, b: int) -> int =>
    b == 0 ? fail "0으로 나눌 수 없음" : a / b
```

호출 지점에서 어떻게 할지 고릅니다:

- `divide(x, y)?` — **전파**: 실패하면 *내* 호출자에게 돌려줍니다.
- `try divide(x, y)` — **구체화**: 실패를 잡아, 되감기는 대신 살펴볼 수 있는
  값으로 받습니다.

```
result = try divide(10, 0)     // 전파하지 않고 여기서 처리
```

> `null`도 예외 계층도 없습니다. 실패는 메시지를 지니고 정확히 두 경로 중
> 하나로 움직입니다: `?`로 계속 가거나, `try`로 내 손에 들어오거나.

## 테스트는 코드 옆에 산다

`maca test`는 프로그램의 테스트를 컴파일해 실행합니다. 따로 배울 프레임워크가
없습니다 — 이름이 `test_`로 시작하는 함수가 곧 테스트입니다:

```
add(a: int, b: int) -> int => a + b

test_add_is_commutative() -> int {
    add(2, 3) == add(3, 2) ? 0 : fail "덧셈은 교환법칙을 만족해야 함"
}
```

`0`을 반환하면 통과, 실패하면 실패이고, 그 메시지가 여러분이 읽을 내용입니다.

## 골든 예제 습관

Maca 컴파일러 자신도 여러분에게 권하는 방식 그대로 개발됩니다: 모든 언어 기능은

- 그것을 쓰는 작은 프로그램을 `examples/`에 두고,
- 그 프로그램을 컴파일하고 실행해 출력을 확인하는 테스트를 갖습니다.

요점은 기능이 실제로 *실행되는* 프로그램에서 돌아갈 때 비로소 "완료"라는
것입니다. 그럴듯해 보이지만 한 번도 실행되지 않은 컴파일러 출력은 그 누구의
버그도 잡아 준 적이 없습니다.

## 행동할 수 있는 진단

컴파일러는 추론 잡음의 벽이 아니라, 작고 의도된 오류 집합을 보고합니다:

- `TypeMismatch` — 타입이 맞지 않음 (호출 인자 개수, 어긋난 `if` 분기 포함),
- `NonExhaustive` — `match`에 빠진 variant가 있음,
- `UndefinedName` — 어디에도 정의되지 않은 것을 호출함,
- `Immutable` — 상수를 재할당함,
- `EffectInConfig` / `UnknownOption` — 설정 모드의 가드레일.

각각은 무엇이 잘못됐고 어디인지를 지목합니다. 행동할 수 없는 진단을 받았다면,
그건 여러분이 아니라 컴파일러의 버그입니다.
